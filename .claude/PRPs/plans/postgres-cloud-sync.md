# Engram Cloud Sync — Postgres как общий мозг

**Статус:** черновик плана
**Дата:** 2026-08-25
**Область:** новая опциональная функциональность. Локальный режим не меняется по умолчанию.

---

## 1. Цель

Дать пользователю возможность подключить несколько устройств к одной памяти Engram, потратив на это одно действие.

**Действие пользователя целиком:**

```bash
engram cloud connect "postgres://user:pass@ep-xxx.neon.tech/engram?sslmode=require"
```

Или, без CLI, одна переменная в конфиге MCP:

```json
{
  "mcpServers": {
    "engram": {
      "command": "npx",
      "args": ["-y", "@engram-ai-memory/mcp@latest"],
      "env": { "ENGRAM_SYNC_URL": "postgres://...?sslmode=require" }
    }
  }
}
```

Всё остальное происходит само: при первом запуске устройство создаёт схему (если её нет), выкачивает всю память в локальную SQLite и дальше синхронизируется в фоне.

Postgres пользователь берёт где угодно — Neon, Supabase, Railway, Render, свой сервер. Аутентификация — родная аутентификация Postgres внутри строки подключения. Никаких аккаунтов, токенов и серверов Engram поднимать не нужно.

## 2. Архитектурное решение

**Local-first, Postgres — узел синхронизации, а не второй бэкенд.**

```
Устройство A                    Устройство B
┌─────────────────┐            ┌─────────────────┐
│ NeuralBrain     │            │ NeuralBrain     │
│ SQLite          │            │ SQLite          │
│ engram.db.index │            │ engram.db.index │
│      ↕          │            │      ↕          │
│  SyncEngine     │            │  SyncEngine     │
└────────┬────────┘            └────────┬────────┘
         │                              │
         └──────────► Postgres ◄────────┘
                   (общая память)
```

`NeuralBrain` продолжает работать **только** на SQLite. Postgres видит один-единственный новый модуль — `SyncEngine`, у которого своя схема и свои pg-запросы.

### Почему так, а не «core на двух диалектах»

1. **Драйвер синхронный.** `better-sqlite3` синхронен, `db.transaction((tx) => {...})` принимает синхронный колбэк. В `transactions.test.ts` это зафиксировано тестом с прямым предупреждением, что переход на async-транзакции или PostgreSQL сломает предположение. Перевод core на PG — это переписывание всех транзакционных путей.
2. **Типы не переносятся.** `blob` эмбеддинга, текстовые `CURRENT_TIMESTAMP`, `sqliteTable` по всей схеме. Drizzle не даёт переносимый билдер между sqlite и pg — это два разных API.
3. **Векторный индекс не в БД.** `engram.db.index` — самописный бинарный кэш рядом с файлом БД, а синхронизация индекса между процессами построена на `PRAGMA data_version`, у которого нет удалённого аналога (`adapter.ts:379-382` возвращает `null` на PG, то есть механизм просто отключается). Если бы core ходил в общий PG, каждое устройство всё равно строило бы свой индекс и не узнавало бы об изменениях с других машин.
4. **Оффлайн бесплатно.** При local-first `recall_context` не получает сетевой задержки, а самолётный режим работает без единой строчки дополнительного кода.
5. **Нулевой риск для существующих пользователей.** Локальный путь кода не трогается вообще.

Цена решения: у устройства есть окно рассинхронизации (по умолчанию ~30 секунд) и нужна стратегия разрешения конфликтов. Это раздел 4.

### Что явно НЕ делаем в этом плане

- Не переводим `NeuralBrain` на Postgres.
- Не требуем pgvector. Эмбеддинги едут в `bytea` побайтово. Это снимает ограничение на хостинг: работает на любом managed Postgres.
- Не поднимаем сервис Engram, аккаунты, биллинг. Аутентификация = строка подключения Postgres.
- Не делаем E2E-шифрование (см. раздел 9, открытые вопросы).
- Не синхронизируем `context_assemblies` (журнал аудита recall, большой объём, нулевая ценность на других устройствах) и `webhooks` (привязаны к конкретной машине).

## 3. Модель данных для синхронизации

### Что синхронизируется

| Таблица | Синк | Комментарий |
|---|---|---|
| `memories` | да | ядро |
| `memory_connections` | да | рёбра графа |
| `sessions` | да | нужны для целостности `session_id` |
| `context_assemblies` | нет | локальный журнал recall |
| `webhooks` | нет | привязаны к устройству |

### Изменения схемы SQLite (обратно совместимые)

Все — через новый блок в `runSqliteMigrations` (`adapter.ts`), версия v0.5.0, идемпотентный `ALTER TABLE ... ADD COLUMN`.

**`memories`:**
- `device_id TEXT` — какое устройство внесло последнюю правку. Нужно для детерминированного разрешения ничьей по времени.
- `updated_at` — гарантировать выставление на **каждом** пути записи (сейчас часть UPDATE его не трогает, см. Фаза 0, задача 0.1).

**`memory_connections`:**
- `deleted_at TEXT` — тумбстоун. Сейчас удаление жёсткое (`tx.delete(...)` в `NeuralBrain.ts:924-931`), на репликах такое удаление не отследить.
- `updated_at TEXT`, `device_id TEXT` — сейчас есть только `created_at`.

**`sessions`:**
- `deleted_at TEXT`, `updated_at TEXT`, `device_id TEXT`.

**Новая таблица `sync_state`:**

```sql
CREATE TABLE IF NOT EXISTS sync_state (
  id                TEXT PRIMARY KEY,     -- sha256(нормализованный sync url)
  device_id         TEXT NOT NULL,
  pull_cursor       TEXT,                 -- server_updated_at последней принятой строки
  last_push_at      TEXT,
  last_sync_at      TEXT,
  last_error        TEXT,
  embedding_model   TEXT,                 -- защита от несовместимых эмбеддингов
  created_at        TEXT NOT NULL
);
```

`device_id` — uuidv4, генерируется один раз и хранится в `~/.engram/device-id` (плюс дублируется в `sync_state`).

### Схема Postgres

Зеркало синхронизируемых таблиц плюс серверные служебные колонки:

```sql
CREATE TABLE memories (
  id                 TEXT PRIMARY KEY,          -- тот же клиентский uuidv4
  ...                                           -- все прикладные колонки как в SQLite
  embedding          BYTEA,                     -- FP16-блоб побайтово
  device_id          TEXT,
  updated_at         TEXT NOT NULL,             -- часы клиента, для LWW
  deleted_at         TEXT,
  server_updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()  -- часы сервера, для курсора
);
CREATE INDEX ON memories (server_updated_at);
CREATE INDEX ON memories (namespace);
```

Ключевой момент: **два разных времени**. `updated_at` — часы устройства, участвует в разрешении конфликтов. `server_updated_at` — часы Postgres, единственное, по чему двигается курсор чтения. Это убирает зависимость от рассинхронизации часов между машинами.

`server_updated_at` обновляется триггером на UPDATE, чтобы клиент не мог его подделать.

Миграции Postgres — настоящие, через drizzle-kit с отдельным конфигом (`drizzle.pg.config.ts`), а не ad-hoc функцией как сейчас.

## 4. Протокол синхронизации

### Цикл

```
sync():
  push()   # локальные изменения → Postgres
  pull()   # чужие изменения → локально
```

Запускается: при старте, по таймеру (`ENGRAM_SYNC_INTERVAL`, по умолчанию 30 с), после записи с дебаунсом, и вручную через `engram cloud sync`.

Синхронизация **никогда не блокирует** `store()` / `recall()`. Ошибка сети — не ошибка операции: записали локально, синхронизируем позже.

### push

```sql
-- локально
SELECT * FROM memories WHERE updated_at > :last_push_at LIMIT 500;

-- в Postgres, батчами
INSERT INTO memories (...) VALUES (...)
ON CONFLICT (id) DO UPDATE SET ...
WHERE EXCLUDED.updated_at > memories.updated_at
   OR (EXCLUDED.updated_at = memories.updated_at
       AND EXCLUDED.device_id > memories.device_id);
```

Условие в `ON CONFLICT` — это и есть last-write-wins с детерминированным разрешением ничьей по `device_id`. Строка старше той, что уже в облаке, молча не применяется.

### pull

```sql
SELECT * FROM memories
WHERE server_updated_at > :pull_cursor - interval '5 minutes'
ORDER BY server_updated_at
LIMIT 500;
```

Окно перекрытия в 5 минут закрывает классическую дыру: транзакция, начавшаяся раньше, но закоммиченная позже прочитанного максимума, иначе была бы пропущена навсегда. Перечитывание безопасно, потому что применение идемпотентно (тот же LWW-upsert, но локально).

Строки, у которых `device_id` = наш собственный, при pull пропускаются — это эхо нашего же push.

### Разрешение конфликтов

| Случай | Правило |
|---|---|
| Одна и та же память отредактирована на двух устройствах | LWW по `updated_at`, ничья — по `device_id` (лексикографически больший выигрывает) |
| `access_count` | **MAX**, а не LWW. Под LWW инкременты с одного устройства затирали бы другие |
| `last_accessed_at` | MAX |
| Удаление против правки | Удаление выигрывает, если его `deleted_at`/`archived_at` новее `updated_at` правки |
| Память создана на A, ребро на неё создано на B | Рёбра применяются после памятей в рамках одного цикла; ребро на отсутствующий узел откладывается до следующего цикла, а не роняет синк |

Отдельный случай — **несовпадение модели эмбеддингов**. Если в `sync_state.embedding_model` или в облаке записана модель, отличная от текущей `ENGRAM_EMBEDDING_MODEL`, векторы несовместимы (разная размерность или разное пространство). Синк обязан остановиться с внятным сообщением и предложить `engram cloud sync --re-embed`, а не молча смешать два несовместимых набора векторов.

### Первое подключение устройства

`pull_cursor` пуст → выкачиваем всё батчами по 500, показываем прогресс, затем `rebuildIndex()` один раз в конце (а не на каждый батч). Для базы в 6 МБ / ~8000 памятей это единицы секунд.

## 5. Фазы

### Фаза 0 — Подготовка схемы к синхронизации

Локальная работа, полностью обратно совместимая. Ценна сама по себе: чинит несколько дефектов, существующих уже сегодня.

**Инвентаризация путей записи проведена, результаты в Приложении А.** Главная находка: `archiveAtomic` не бампает `updated_at`, а через него проходит каждый `forget()` и каждая консолидация. При наивной реализации push (`WHERE updated_at > last_push_at`) **удаление памяти никогда бы не уехало в облако** — память исчезала бы локально и молча воскресала при следующем pull. Это первое, что нужно починить.

**Файлы:** `packages/core/src/db/schema.ts`, `packages/core/src/db/adapter.ts`, `packages/core/src/NeuralBrain.ts`, `packages/core/src/retrieval/ContextAssembler.ts`, `apps/server/src/routes/{graph,analytics}.ts`

**0.1 Починить UPDATE, не бампающие `updated_at`.** Четыре сайта:

| Сайт | Что делает | Последствие для синка |
|---|---|---|
| `NeuralBrain.ts:919-922` (`archiveAtomic`) | ставит `archivedAt` | **критично** — удаление не распространяется |
| `NeuralBrain.ts:1870-1873` (`resolveContradiction`) | ставит `archivedAt` | то же |
| `NeuralBrain.ts:1669-1678` (`backfillEmbeddingModel`) | ставит `embeddingModel` | расхождение метаданных между устройствами |
| `ContextAssembler.ts:198-204`, `:390-396` | `accessCount + 1`, `lastAccessedAt` | намеренно оставляем как есть, см. 0.6 |

**0.2 `memory_connections`.** У таблицы нет `updated_at` вообще (`schema.ts:77-107`) — строки только вставляются или жёстко удаляются. Добавить `updated_at`, `deleted_at`, `device_id`.

**0.3 Заменить три жёстких удаления рёбер на тумбстоуны:** `NeuralBrain.ts:924-931` (`archiveAtomic`), `:1875-1882` и `:1888-1898` (`resolveContradiction`). Все чтения графа фильтруют `deleted_at IS NULL`.

**0.4 `sessions`.** Тоже нет `updated_at`; добавить вместе с `deleted_at` и `device_id`.

**0.5 Нормализовать формат времени.** Два сайта не передают время явно и полагаются на SQLite-дефолт `CURRENT_TIMESTAMP`: `NeuralBrain.ts:963-969` (`createSession` не передаёт `startedAt`) и `ContextAssembler.ts:213-230`, `:401-416` (`context_assemblies` не передаёт `createdAt`). Дефолт даёт `"2026-08-25 14:23:01"` — секундная точность, без `T` и без `Z`, тогда как все остальные сайты пишут `"2026-08-25T14:23:01.123Z"`. Любой компаратор LWW на такой смеси сломается. Передавать `new Date().toISOString()` явно.

**0.6 Вывести `access_count` из-под LWW.** Инкремент идёт сырым SQL `col + 1` и `updated_at` не трогает — и это правильно оставить как есть. Бампать `updated_at` на каждом recall означало бы гнать в облако десятки строк на каждый ход агента. Счётчик синхронизируется отдельным правилом MAX (Фаза 2) и не считается изменением для целей push. Уточнение из инвентаризации: `brain.search()` счётчик не трогает вообще, только `recall()` / `recallStream()`, 5-20 строк за вызов.

**0.7 Три прямые Drizzle-записи в `apps/server`, минующие `NeuralBrain`:** `routes/graph.ts:158` (INSERT ребра), `routes/analytics.ts:163-166` (PATCH памяти), `routes/analytics.ts:218-221` (bulk tag). Две последние `updated_at` ставят, первая — нет и не может, потому что колонки пока не существует. После 0.2 привести все три к общему инварианту.

**0.8** Таблица `sync_state` + генерация и хранение `device_id`.

**0.9** Починить устаревшую drizzle-миграцию `0000_cynical_marauders.sql` — она не знает про `namespace`, `embedding_model` и `webhooks`, то есть `drizzle-kit migrate` сегодня даёт схему, не совпадающую с рантайм-схемой.

**Критерии приёмки:**
- Существующий набор тестов зелёный без изменений.
- Тест: свежая БД и БД, поднятая миграцией со старой версии, дают идентичную схему (сравнение `PRAGMA table_info` по всем таблицам).
- **Тест на главную находку:** `forget(id)` строго увеличивает `updated_at` этой памяти; то же для `resolveContradiction` и `consolidate`.
- Обратный тест: `recall()` **не** меняет `updated_at` (защита от регрессии в другую сторону).
- Тест: значения всех timestamp-колонок во всех таблицах матчатся на `/^\d{4}-\d{2}-\d{2}T.*Z$/`.
- Тест: удалённое ребро не возвращается в обходе графа, но физически присутствует в таблице с `deleted_at`.
- Миграция идемпотентна: двукратный прогон на одной БД не падает.
- **Прогон по копии реальной БД.** Синтетические фикстуры не показывают того, что показывают настоящие данные: легитимные `NULL` в `embedding_model`, реальные namespace, реальный объём. Скрипт `scripts/verify-migration-against-real-db.mjs <путь-к-бэкапу>` копирует указанную БД во временный файл, прогоняет по копии миграцию через адаптер и проверяет:
  - количество строк в каждой таблице до и после совпадает;
  - выборка записей читается, содержимое и блобы эмбеддингов побайтово не изменились;
  - `PRAGMA table_info` по всем таблицам совпадает со свежесозданной БД;
  - новые колонки присутствуют и заполнены `NULL`.

  Оригинал никогда не открывается — только копия. Скрипт остаётся в репозитории как инструмент для всех будущих миграций, но **не** оформляется как vitest-тест: он зависит от приватной БД, которой нет в CI.

### Фаза 1 — Схема и подключение Postgres

**Файлы:** новый `packages/core/src/db/pg/schema.ts`, `packages/core/src/db/pg/migrations/`, `packages/core/drizzle.pg.config.ts`, правка `packages/core/src/db/adapter.ts`

- **1.1** `pgTable`-схема для `memories`, `memory_connections`, `sessions` + `server_updated_at`, индексы, триггер обновления `server_updated_at`.
- **1.2** Настоящие миграции через drizzle-kit (`pnpm db:generate:pg`), применяются автоматически при первом подключении.
- **1.3** Убрать мёртвый код: `ENGRAM_DATABASE=postgresql`, `ENGRAM_PG_SCHEMA_READY`, `createPostgresConnection`, `runPostgresMigrations` (`adapter.ts:311-428`). Вместо заглушки-исключения — понятная ошибка: «PostgreSQL как основной бэкенд не поддерживается; для нескольких устройств используйте `ENGRAM_SYNC_URL`, см. docs/CLOUD-SYNC.md».
- **1.4** Пул соединений с ограничением (managed Postgres на бесплатных тарифах даёт мало коннектов; `max: 2` достаточно), обязательный `sslmode=require` с явным opt-out флагом.

**Критерии приёмки:**
- Тесты на реальном Postgres через `@testcontainers/postgresql` (пропускаются, если Docker недоступен; в CI — сервис-контейнер в `ci.yml`).
- Схема создаётся с нуля на пустой БД; повторный запуск не падает.
- Round-trip тест на каждую синхронизируемую таблицу: запись → чтение → байтовое совпадение, включая `embedding` BYTEA.
- Строка подключения без `sslmode` отклоняется с внятной ошибкой.

### Фаза 2 — SyncEngine

**Файлы:** новый каталог `packages/core/src/sync/` — `SyncEngine.ts`, `PgSyncClient.ts`, `conflict.ts`, `cursor.ts`, `deviceId.ts`

- **2.1** `push()`, `pull()`, `fullSync()`, `status()` по протоколу из раздела 4.
- **2.2** Разрешение конфликтов в `conflict.ts` как чистые функции без побочных эффектов — они должны быть покрыты тестами напрямую, без БД.
- **2.3** Батчинг по 500, экспоненциальный backoff при ошибках сети, устойчивость к оффлайну.
- **2.4** Проверка совместимости модели эмбеддингов при подключении. Учесть находку инвентаризации: `embedding_model` заполняется **только** в `NeuralBrain.store()` (`NeuralBrain.ts:632`); записи через публичные `brain.episodic` / `brain.semantic` / `brain.procedural` оставляют колонку `NULL`. Проверка обязана трактовать `NULL` как «неизвестно, считаем совместимым» и предлагать `backfillEmbeddingModel()`, а не падать.
- **2.5** Фоновый планировщик: интервал + дебаунс после записи. Корректная остановка при завершении процесса.

**Критерии приёмки:**
- Тест конвергенции: две временные SQLite + один Postgres, имитация устройств A и B; после `sync()` на обоих содержимое совпадает побайтово.
- Тест идемпотентности: пятикратный `sync()` без изменений не создаёт дублей и не двигает данные.
- Тест оффлайна: запись при недоступном Postgres проходит успешно, после восстановления связи сходится.
- Тест конфликта: одновременная правка одной памяти на A и B разрешается детерминированно и одинаково с обеих сторон.
- Тест удаления: удаление на A убирает память на B.
- Тест счётчика: `access_count` после синка равен максимуму, а не значению последнего писателя.
- Тест несовместимой модели: синк останавливается с понятным сообщением и не портит векторы.
- Покрытие `packages/core/src/sync/**` не ниже 80% по строкам.

### Фаза 3 — Конфигурация и UX

### Фаза 4 — Безопасность

**Файлы:** `packages/core/src/sync/*`, `apps/server/src/index.ts`

- **4.1** Редактирование секретов: пароль из строки подключения не должен попадать ни в логи, ни в текст ошибок, ни в вывод `status`. Тест: намеренно неверный пароль, проверить, что он не встречается в перехваченном выводе.

Там же — отсутствие rate limiting и security-заголовков.

**Критерии приёмки:**
- Тест на неутечку пароля.
- Тест: подключение к Socket.io без валидного ключа отклоняется, когда `ENGRAM_API_KEY` задан.

## 7. Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Расхождение часов между устройствами ломает LWW | Правки теряются | Курсор двигается по серверному времени; клиентское время только для LWW, где расхождение в секунды не критично |
| Пропуск строк из-за коммитов не по порядку | Тихая потеря данных | Окно перекрытия 5 минут при pull + идемпотентное применение |
| Разные модели эмбеддингов на устройствах | Мусорный поиск | Жёсткая проверка при подключении, остановка синка |
| Бесплатные тарифы Postgres засыпают | Синк падает по таймауту | Backoff, оффлайн — не ошибка, `status` показывает причину |

## 8а. Развилка Turso — закрыта 2026-08-26

Рассматривалась альтернатива: взять Turso embedded replicas и получить движок синхронизации готовым, не делая Фазу 2. **Отклонено.**

**Причина — многопроцессность.** Документация Turso, для обеих генераций синхронизации, требует: *«Do not open the local database file with another process while it is actively syncing — you risk corruption»*, а мануал Turso Database держит «No multi-process access» в списке ограничений движка. Engram по устройству открывает один файл из REST-сервера, MCP-сервера и CLI одновременно — и механизм `PRAGMA data_version` существует именно ради этого. Turso запрещает то, на чём система стоит.

Сопутствующие факты:
- Офлайн-запись живёт только в Turso Sync (Beta, октябрь 2025) поверх Turso Database — переписки SQLite на Rust, не достигшей 1.0. На Turso Cloud связка помечена early preview.
- `PRAGMA data_version` значится как не поддерживаемый в COMPAT.md движка.
- Pull только вручную, авто-интервала в новом движке нет.
- Автоматический checkpoint для sync-баз отключён — WAL растёт неограниченно у постоянно работающего процесса.
- Бесплатный тариф: отдельная квота 3 ГБ/месяц на синхронизацию; превышение даёт жёсткую ошибку `BLOCKED`.

**Что подтвердилось в пользу текущего плана:** модель конфликтов Turso Sync — last-push-wins на уровне строки плюс хук для своей логики, без CRDT. Это независимое подтверждение, что LWW по `updated_at` с разрешением ничьей по `device_id` (раздел 4) — правильный выбор, а не упрощение.

**Заодно измерена цена перехода ядра на async-драйвер** (актуально, если тема всплывёт снова): она оказалась НИЖЕ ожидаемой. Билдеры Drizzle поверх better-sqlite3 — thenable, поэтому в коде уже почти везде написано `await`; публичных сигнатур меняется 0–2, потребители (`apps/server`, `packages/mcp`) почти не задеты. Настоящая работа концентрируется в четырёх телах транзакций (libSQL атомарен через `batch()` с заранее известным списком утверждений, а три из четырёх собирают его условно), в `getDeviceId()` (станет асинхронным — вернётся гонка, но уже внутрипроцессная, понадобится single-flight) и в замене `PRAGMA data_version`.

## 9. Открытые вопросы

1. **Шифрование.** Сейчас в плане его нет: администратор Postgres видит содержимое памяти. Для собственной Neon-базы это нормально. Нужен ли флаг E2E? Оговорка: при E2E серверный поиск невозможен в принципе, но в текущей архитектуре поиск и так локальный, так что цена ниже обычной.
2. **`context_assemblies`.** Точно не синхронизируем? Это журнал recall — на другом устройстве может быть полезен для аналитики, но объём растёт быстро.
3. **Несколько людей на одной БД.** Разделять только через `namespace`, или сразу закладывать колонку `tenant_id` и RLS, чтобы позже не мигрировать?
4. **Что делать со старым `ENGRAM_DATABASE=postgresql`.** План предлагает удалить мёртвый код. Альтернатива — оставить как задел под Фазу 6.
5. **Ретеншен тумбстоунов.** Удалённые строки копятся вечно. Нужна политика вычистки (например, старше 90 дней), но она должна быть безопасна для устройства, которое не выходило на связь дольше этого срока.

## Приложение А — Инвентаризация путей записи

Проведена по `packages/core/src` и `apps/server/src/routes`. Факты, на которых стоит план.

**Пути записи в `memories`:** 17 сайтов. `updated_at` не выставляют четыре: `NeuralBrain.ts:919-922`, `:1669-1678`, `:1870-1873`, `ContextAssembler.ts:198-204` / `:390-396`.

**Жёсткие удаления.** Ни один путь кода нигде не делает физический `DELETE FROM memories`, `sessions` или `context_assemblies` — память только архивируется через `archived_at` и никогда не вычищается, job-а очистки не существует. Жёсткие `DELETE` есть только по `memory_connections` (три сайта, см. 0.3) и `webhooks` (`WebhookManager.ts:134`, таблица не синхронизируется).

**Каскад.** `memory_connections.source_id` / `target_id` объявлены `ON DELETE CASCADE` на `memories.id` (`schema.ts:83,86`, `adapter.ts:195-196`), и `foreign_keys = ON` включён на каждом соединении (`adapter.ts:128`). Сегодня каскад спит, потому что физических удалений памяти нет. Но он проснётся, если когда-нибудь появится вычистка старых тумбстоунов (открытый вопрос 5): рёбра исчезнут через каскад, минуя прикладной код очистки.

**`archived_at`.** Ставится в двух местах, **никогда не сбрасывается обратно** — метода «восстановить» в core нет. Сweep увядания только архивирует, физически не удаляет.

**Эмбеддинги.** FP16, little-endian, 2 байта на компонент (`Embedder.ts:144-161`). По умолчанию 384 измерения = 768 байт; максимум среди поддерживаемых моделей 768 измерений = 1536 байт. Порядок байт задан явно и не зависит от платформы, поэтому блоб переносится в Postgres `bytea` побайтово без преобразований — план на `bytea` подтверждён. `embedding_dim` заполняется всегда; `embedding_model` — **не всегда** (см. 2.4).

**Идентификаторы.** Все PK во всех таблицах — клиентские `uuidv4()`, ни одного DB-дефолта и ни одного контентного хэша. Для LWW-синка это идеально: коллизий при независимой генерации на разных устройствах не бывает.

**Формат времени.** Доминирует `toISOString()` с миллисекундами. Исключения — два сайта, полагающиеся на `CURRENT_TIMESTAMP` (см. 0.5).

**`access_count`.** Инкрементируется сырым SQL `col + 1` именно для того, чтобы параллельные recall не затирали друг друга — то есть колонка изначально спроектирована как write-hot. Это прямое подтверждение, что LWW для неё не годится.
